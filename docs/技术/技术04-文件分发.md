> 依赖通用框架：`docs/技术/技术03-统一任务架构.md`（TaskManager / 暂存管理 / SSE / useTaskManager / TaskViewerButton）
>

>
> 对应需求：`docs/需求/需求03-文件分发.md`

## 1. 概述

文件分发 = **暂存**（前端文件 → 后端磁盘）+ **分发**（后端磁盘 → N 个 S3 实例）。

两阶段解耦的设计意义：

- 暂存是前端 XHR，与 SSE 解绑，离开页面即中断——因此暂存阶段**不能后台继续**。
- 分发是后端 TaskManager 任务，与连接解绑——因此分发阶段**可以后台继续**。

**upload 与 dispatch 的关系**：实例访问页的上传本质是"单实例分发"——暂存到同一磁盘目录，分发时目标实例 = 1。统一任务架构下，`DispatchExecutor` 用目标实例数 N=1 即复用为 `UploadExecutor`（上传后续技术方案再展开，本文不实现）。本文只实现分发页 + `DispatchExecutor`。

```
┌ 前端 ────────────────────────────────────────────────────────┐
│  分发页 dispatch/index.vue                                      │
│    ① 选文件 + 选目标实例/bucket/prefix（idle）                  │
│    ② 暂存：XHR 逐文件 POST /api/dispatch/stage（staging）       │
│    ③ 提交分发：POST /api/dispatch → taskId（dispatching）       │
│    ④ SSE 订阅：useTaskManager().subscribeTask(taskId)           │
│    ⑤ 后台继续：页面重置为 idle，任务查看器全局可见              │
└──────────────────────────────────────────────────────────────┘
            │ ② multipart/form-data 流式落盘        │ ③ JSON
            ▼                                        ▼
┌ 后端 ────────────────────────────────────────────────────────┐
│  staging.stageFile()  ──磁盘──>  DispatchExecutor.execute()    │
│  (server/utils/staging.ts)        (server/utils/executors/)    │
│                                         dispatch.ts            │
│                                   ┌─────────────────────────┐ │
│                                   │ 实例维度并发 (默认 5)    │ │
│                                   │ 实例内文件串行           │ │
│                                   │ 单次 PUT（不引入分片）   │ │

└──────────────────────────────────────────────────────────────┘
```

## 2. DispatchExecutor（server/utils/executors/dispatch.ts）

实现 `TaskExecutor` 接口（见通用框架 §4）：

```ts
interface TaskExecutor {
  execute(task: Task, emit: (event: TaskEvent) => void, isCancelled: () => boolean): Promise<void>
}
```

### 2.1 接口与构造

```ts
import type { TaskExecutor } from '#shared/schemas/task'
import type { TaskEvent, InstanceProgress, FileResult } from '#shared/schemas/task'

/** 分发任务参数（由 POST /api/dispatch 构造后传入） */
export interface DispatchParams {
  files: { fileId: string; objectKey: string }[]   // 已暂存的文件 + 落盘 objectKey
  targets: { instanceId: string; instanceName: string; bucket: string }[]
  prefix: string                                    // 全局目标前缀（已由后端 sanitizeObjectKey 清洗）
}

export function createDispatchExecutor(params: DispatchParams): TaskExecutor
```

> 执行器是「每任务一个实例」——`createDispatchExecutor(params)` 闭包捕获参数，返回的 `TaskExecutor` 注册到 `TaskManager.createTask()`。任务结束后实例即丢弃。

### 2.2 execute 方法逻辑

```ts
async execute(task, emit, isCancelled) {
  const stagedFiles = getStagedFiles(params.files.map(f => f.fileId))

  // 1. 初始化实例维度进度矩阵 instanceProgress[]
  //    每个 target 一项，results 预填所有 objectKey = { status: 'pending' }
  // 2. 同步到 task.instanceProgress（供 SSE 快照重连恢复）

  emit({ event: 'start', data: { taskId: task.taskId } })

  // 3. 实例维度并发：DISPATCH_CONCURRENCY 个实例同时分发
  //    用简单的并发池（Promise 池），实例内文件串行
  await runConcurrentPool(params.targets, DISPATCH_CONCURRENCY, async (target) => {
    const instance = getInstanceById(target.instanceId)        // 从 store 读取 MinioInstance
    for (const f of stagedFiles) {
      // 取消检查点：每文件开始前检查
      if (isCancelled()) {
        markRemainingSkipped(target, f.objectKey)              // 未开始的标记 skipped
        return
      }

      const fullKey = buildFullKey(params.prefix, f.objectKey) // prefix/objectKey
      const contentType = inferContentType(f.originalName)     // 显式 Content-Type

      // 标记 running，emit progress（instanceId 字段供前端定位实例行）
      setResult(target, f.objectKey, { status: 'running' })
      emitProgressRunning(...)

      const start = Date.now()
      try {
        // 单次 PUT：readFile 读暂存磁盘 Buffer，uploadObjectStream 上传
        const body = await readFile(f.diskPath)
        await uploadObjectStream(instance, target.bucket, fullKey, body, contentType, f.size)
        setResult(target, f.objectKey, { status: 'success', duration: Date.now() - start })
      } catch (e) {
        setResult(target, f.objectKey, { status: 'failed', error: formatError(e), duration: Date.now() - start })
      }
      emitProgressDone(target, f.objectKey)   // 成功/失败都 emit，前端更新矩阵
    }
  })

  // 4. 汇总 summary（total = targets.length × files.length）
  //    走取消分支时按 cancelRequested 设置 task.status，由 TaskManager 决定 done/cancelled

  // 5. 清理暂存文件（分发完成后无论成功失败都清理磁盘）
  await Promise.all(stagedFiles.map(f => removeStagedFile(f.fileId)))
}
```

### 2.3 实例维度并发

- **并发模型**：实例维度并发，实例内文件串行。默认 `DISPATCH_CONCURRENCY = 5`。
- **实现**：简单的 Promise 并发池，从 targets 数组取 N 个同时跑，完成一个补一个。
- **隔离性**：某实例整体失败（连接拒绝）只标记该实例所有文件 failed，不影响其他实例。
- **不设实例内文件并发**：避免对单实例造成过大压力，且简化进度展示（实例内文件按顺序可见）。

### 2.4 上传策略

| 文件大小 | 策略 | 实现 |
| --- | --- | --- |
| 任意大小 | 单次 PUT | `readFile(f.diskPath)` → Buffer → `uploadObjectStream()` |

```ts
import { readFile } from 'node:fs/promises'
import { uploadObjectStream } from '#server/utils/minio'

const body = await readFile(f.diskPath)
await uploadObjectStream(instance, bucket, fullKey, body, contentType, f.size)
```

> **不引入 S3 Multipart Upload。** 原稿"≥8MB 分片"引用的是模板重置（269671c）前已废弃的代码，dispatch 重写（864e842）时未搬过来，上传改造（技术05）也明确与现状对齐。若未来出现真实大文件需求，再为 dispatch + upload 一并升级。

### 2.5 内存与磁盘

分发是「磁盘 → 对象存储」。当前实现 `readFile` 将整个文件读入 Buffer 后 PUT，内存占用约等于单文件大小（实例内文件串行，同时只有一个文件在内存中）。超大文件场景需评估后再考虑分片或流式 PUT。

### 2.6 取消检查点

通用框架 `cancelTask()` 设置 `cancelRequested = true`，`isCancelled()` 回调读取它。DispatchExecutor 在**每文件开始前**检查：

`if (isCancelled()) { markRemainingSkipped(target, f.objectKey); return }`——未开始的文件标记 `skipped`，与 `failed` 区分。

> 正在传输的单次 PUT 不中断（无分片可 abort），该文件跑完后停止后续文件。已完成上传的文件保留在目标实例（不回滚），符合需求 §7.1。

### 2.7 完成后清理暂存文件

`execute()` 末尾 `Promise.all(stagedFiles.map(f => removeStagedFile(f.fileId)))` 删除磁盘暂存文件。无论任务成功/失败/取消都执行（放到 try-finally）。孤儿清理（`cleanupOrphanedFiles`）兜底处理进程重启等异常残留。

### 2.8 instanceProgress（实例维度进度矩阵）

DispatchExecutor 用 `InstanceProgress[]` 维护进度（通用框架 §3 类型定义），区别于 copy/move/upload 的扁平 `FlatFileProgress`：

```ts
// task.instanceProgress 结构
[
  {
    instanceId: 'inst-1', instanceName: '生产主节点', bucket: 'config',
    results: {
      'config.json': { status: 'success', duration: 320 },
      'logo.png':    { status: 'failed', error: '403 Access Denied', duration: 120 },
      'data.yaml':   { status: 'pending' },
    }
  },
  // ... 更多实例
]
```

- 每次 `setResult` 更新 `task.instanceProgress[i].results[key]`，同时 `emit('progress', { taskId, objectKey, result, instanceId })`。
- `instanceId` 字段让前端 progress 事件能定位到具体实例行（通用框架 `TaskEvent` 已包含 `instanceId?`）。
- 该矩阵也用于 SSE 重连恢复：前端断线后 `GET /api/tasks/:taskId/state` 返回含 `instanceProgress` 的快照，重建视图。

## 3. API 路由

### 3.1 POST /api/dispatch/stage — 暂存单个文件

`multipart/form-data`，逐文件调用。前端 XHR 流式上传，落盘到暂存目录。

```ts
// server/api/dispatch/stage.post.ts
export default defineEventHandler(async (event) => {
  const form = await readMultipartFormData(event)
  const file = form?.find(f => f.name === 'file')        // 单文件字段
  const objectKey = form?.find(f => f.name === 'objectKey')?.data.toString('utf8')

  // 1. 校验 MAX_UPLOAD_SIZE
  // 2. sanitizeObjectKey(objectKey) 清洗路径
  // 3. stageFile(buffer, objectKey, file.filename, inferContentType(objectKey)) 落盘
     //    Content-Type 按扩展名推断，不信任 file.type：
     //    Bun 运行时 formData() 会给 multipart part 的 Content-Type 追加 ;charset=utf-8，
     //    该值原样写入对象存储后会导致 Console 无法预览（Node/undici 无此行为）
  // 4. 返回 { fileId }
  return { fileId: stagedFile.fileId }
})
```

| 项 | 说明 |
| --- | --- |
| 请求体 | `multipart/form-data`：`file`（文件）+ `objectKey`（落盘 key，文件夹内文件带相对路径） |
| 返回 | `{ fileId: string }` |
| 大小限制 | `MAX_UPLOAD_SIZE`（默认 0=不限），超限返回 413 |
| 路径安全 | `sanitizeObjectKey` 防路径遍历 |

> 暂存路由**不创建 TaskManager 任务**，不进执行队列（暂存不排队，见交互 §7.4）。它只是把文件写到磁盘并登记到 `staging.ts` 的内存 Map。

### 3.2 POST /api/dispatch — 提交分发任务

提交时所有文件已暂存完成，本路由只创建任务并立即返回 `taskId`。

```ts
// server/api/dispatch/index.post.ts
export default defineEventHandler(async (event) => {
  const body = await readBody(event)
  // body: { files: { fileId, objectKey }[], targets: { instanceId, bucket }[], prefix: string }

  // 1. 校验：files 非空、targets 非空、fileId 均已暂存（getStagedFiles）
  // 2. 未指定 bucket 的 target：构造时即标记该实例所有文件 failed（不阻断其他实例）
  // 3. prefix 经 sanitizeObjectKey 清洗
  // 4. 拼装 instanceName（从 store 读实例名）
  // 5. createDispatchExecutor(params) -> createTask(description, executor) -> 返回 taskId
  return { taskId }
})
```

**请求体**：

```ts
{
  files: { fileId: string; objectKey: string }[]
  targets: { instanceId: string; bucket: string }[]
  prefix: string
}
```

- `files`：暂存阶段逐文件拿到的 `fileId` + 前端计算的 `objectKey`（单文件=文件名，文件夹内=相对路径）。
- `targets`：选中的实例 + 各自 bucket。前端把实例树勾选结果扁平化为此数组。
- `prefix`：全局目标前缀，留空=根。最终 key = `prefix/objectKey` 由后端拼接。

**返回**：`{ taskId: string }`

**任务描述**（任务查看器展示）：

```ts
{
  type: 'dispatch',
  label: `分发 -> ${targets.length} 个实例`,
  detail: `${files.length} 个文件`
}
```

## 4. 前端

### 4.1 分发页（app/pages/dispatch/index.vue）

从原型 `app/pages/dispatch/proto/index.vue` 迁移，对接真实 API。布局保留原型左右双栏（左实例树 / 右文件列表·进度卡片·提交栏）。

**阶段机（phase）**：

| phase | 触发 | 行为 |
| --- | --- | --- |
| `idle` | 初始 / 新建分发 | 选文件 + 选目标，按钮「开始分发」 |
| `staging` | 点击「开始分发」 | XHR 逐文件调 `POST /api/dispatch/stage`，展示扁平文件列表 + 上传百分比；按钮仅「取消暂存」 |
| `dispatching` | 暂存全部完成 | `POST /api/dispatch` 提交 → `useTaskManager().subscribeTask(taskId)` 订阅 SSE；按钮「后台继续」+「取消分发」 |
| `done` | SSE `complete` | 进度卡片状态图标变绿/黄，按钮「新建分发」；有失败实例显示「重试」 |
| `cancelled` | SSE `cancelled` | 进度卡片状态图标变灰，按钮「新建分发」；失败/未完成实例可重试 |

**暂存阶段**（`staging`）：

- XHR 逐文件调 `POST /api/dispatch/stage`（`multipart/form-data`）。
- 用 `XMLHttpRequest` 而非 `$fetch`，因需要 `upload.onprogress` 回调拿上传百分比。
- 每文件暂存完成存 `fileId`，失败标记 ❌ + 错误信息，不影响其他文件。
- 进度卡片展示扁平文件列表 + 每行上传进度条 + 百分比（沿用原型 staging 视图）。
- **不能后台继续**：暂存是前端 XHR，离开页面中断。提交栏只有「取消暂存」。
- 取消暂存：`xhr.abort()` 未完成请求，回到 idle，已暂存文件由后端 TTL 清理。

**分发阶段**（`dispatching`）：

- 全部暂存成功后，`POST /api/dispatch` 提交（传 `files`/`targets`/`prefix`），拿 `taskId`。
- `useTaskManager().subscribeTask(taskId)` 订阅 SSE：先 `GET /api/tasks/:taskId/state` 拿快照重建 `instanceProgress` 矩阵，再 `EventSource` 接收增量 `progress` 事件更新矩阵。
- 进度卡片切换为实例维度聚合视图（顶部汇总 + 总进度条 + 实例级折叠列表 + 文件明细），沿用原型 dispatching 视图。
- **后台继续**：页面重置为 idle 状态（清空文件列表、进度矩阵、taskSummary），任务在后端继续。navbar 任务查看器全局可见。
- **取消分发**：`useTaskManager().cancelTask(taskId)` → `POST /api/tasks/:taskId/cancel`，后端设 `cancelRequested`，执行器在检查点停止。

**分发完成**：

- 全部成功：进度卡片图标 ✅ 绿，按钮变「新建分发」。
- 有失败：进度卡片图标 ⚠ 黄，失败实例行显示「重试」按钮。
- 已取消：进度卡片图标 ⊘ 灰，未完成实例可重试。

**失败重试**：

- 失败实例行的「重试」按钮：从当前 `instanceProgress` 提取该实例 `status==='failed'` 的 objectKey，重新提交分发。
- 目标收窄为该单实例 + 其 bucket，文件列表为失败文件（需重新暂存——因上次暂存文件已被清理，重试时重新走 staging→dispatching）。
- 新任务有新 `taskId`，进度区切换为新任务 SSE。

### 4.2 从原型迁移的改动点

| 维度 | 原型 mock | 实现真实 |
| --- | --- | --- |
| 实例数据 | 硬编码 `groups` ref（MockInstance/MockGroup） | 从 `GET /api/manage/groups` 拉真实分组+实例（复用实例管理页数据源） |

## 7. 环境变量

分发专属环境变量（通用框架的环境变量见技术03 §8）：

| 环境变量 | 默认值 | 说明 |
| --- | --- | --- |
| `DISPATCH_CONCURRENCY` | 5 | 分发实例维度并发数（队列内单任务的并发度） |
| `TASK_DELAY_MS` | 0 | 测试用：每文件上传前人为延时（毫秒），便于验证排队/后台继续 |

读取方式沿用项目惯例 `Number(process.env.X) || 默认值`。
