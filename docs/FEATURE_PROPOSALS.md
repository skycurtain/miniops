# miniops 功能改进与扩展提议

> 基于对 miniops 现有代码库的完整分析，从产品功能和用户体验角度提出的改进建议。
>
> 每项提议包含：**解决的痛点**、**功能描述**、**用户使用方式**、**实现要点**、**优先级**。

---

## 一、现状总结

miniops 当前已实现的核心能力：

| 模块 | 能力 |
|---|---|
| 实例管理 | 实例组 CRUD、组内实例增删改查、复制、启停、导入/导出 |
| 连通性测试 | 对单个或组内全部实例做 `/minio/health/live` 健康检查 |
| 文件分发 | 文件/文件夹暂存 → 逐实例并发分发（小文件 PUT / 大文件 Multipart） |
| 进度推送 | SSE 实时推送，实例级聚合折叠视图，失败实例单独重试 |

**识别到的核心缺口**（按影响面排序）：

1. 分发结果不持久化，刷新即丢失，无历史追溯
2. 无法在平台内浏览/管理 MinIO 对象，只进不出
3. 无用户认证，MinIO 密钥明文存储
4. 无法跨实例同步文件（只能从本地上传）
5. 无定时/计划任务能力
6. 无操作审计

## 二、改进提议

### 提议 1：对象浏览器（Object Browser） ✅ 已实现

**解决的痛点**

当前 miniops 只能"往 MinIO 推文件"，无法"看 MinIO 里有什么"。用户要查看分发结果，必须另开 MinIO Console 或用 mc 客户端，操作割裂。特别是分发失败后，用户无法在平台内确认目标 bucket 是否已有同名文件、前缀路径是否正确。

**功能描述**

在实例管理或独立页面中，为每个启用的实例提供对象浏览能力：
- 列出指定 bucket 下的对象/前缀（S3 ListObjectsV2）
- 支持按前缀路径层级导航（进入"虚拟文件夹"）
- 显示对象名、大小、最后修改时间、Content-Type
- 支持删除单个/批量删除对象
- 支持递归删除虚拟文件夹（按前缀列出全部对象后批量删除，含 10000 个上限保护）
- 支持下载对象到本地（通过后端代理流式返回）
- 支持批量 ZIP 打包下载（混合选中对象和文件夹，递归打包保留目录结构）
- 支持生成临时预签名下载 URL
- 支持对象内容预览（图片/视频/音频/PDF 内联渲染，文本 fetch 后高亮展示），在平台内即可确认文件内容，无需下载

**用户使用方式**

1. 进入「对象浏览」页面
2. 选择一个已启用的实例 → 后端调用 ListBuckets 获取 bucket 列表
3. 选择一个 bucket → 展示根级对象列表
4. 点击前缀文件夹可逐层进入；点击对象可预览、下载或删除
5. 支持多选 + 批量删除（带二次确认）
6. 点击预览按钮弹出侧抽屉，按文件类型展示内容（图片/视频/音频/PDF 内联渲染，文本代码展示）

**实现要点**

- 后端新增 `server/utils/minio.ts` 中的 `listObjects()`（S3 ListObjectsV2 API，需手写 SigV4 签名 + XML 解析）
- 新增 `deleteObject()` / `deleteObjects()`（S3 DeleteObject / DeleteMultipleObjects）
- 新增 `presignGetUrl()`（复用现有 presignPutUrl 逻辑，改为 GET 方法）
- API 路由：`POST /api/instances/objects/list`、`POST /api/instances/objects/delete`、`GET /api/instances/objects/download`
- 前端新增 `app/pages/ops/browser/index.vue` 页面
- ListObjectsV2 的 XML 响应需解析 `<Contents>` 和 `<CommonPrefixes>`（前缀分组）
- 对象预览：复用 download 路由加 ?inline=1 参数实现内联渲染；文本类 fetch 后转义展示；不支持浏览器原生渲染的格式提示下载

**优先级**：🔴 高（P0）— 现场需确认 MinIO 内容、核对分发结果，是运维闭环的关键一环

### 提议 2：分发历史记录与持久化

**解决的痛点**

当前分发任务结果只存在内存 `taskRegistry` 中，任务完成后 60 秒即被删除。用户刷新页面、重启服务、或 60 秒后返回，进度和结果全部丢失。无法回溯"上次分发了什么、哪些失败了"，只能靠 `sessionStorage` 里一条极简摘要。对于运维场景，"谁在什么时候向哪些实例分发了什么文件"是必须可追溯的。

**功能描述**

- 每次分发任务自动落盘记录，持久存储
- 历史记录页面：按时间倒序展示所有分发任务
- 每条记录含：任务 ID、时间、文件列表、目标实例、每个实例×文件的成功/失败状态、错误信息、耗时
- 支持按状态（成功/部分失败/全部失败）、实例组、时间范围筛选
- 支持点击查看任务详情（完整结果矩阵）
- 支持"基于此任务再次分发"（一键复用上次的文件、实例、bucket 配置）

**用户使用方式**

1. 左侧导航进入「分发历史」页面
2. 查看历史任务列表，可按状态/时间筛选
3. 点击某条记录查看详情：展开看每个实例每个文件的结果
4. 失败的记录可点击「重试失败项」或「全部重发」
5. 成功的记录可点击「复制配置」跳转到分发页，预填相同的实例和 bucket（文件需重新上传）

**实现要点**

- 存储方案：在 `server/data/` 下新增 `dispatch-history.json`（初期）或 SQLite（长期，推荐 better-sqlite3）
- `dispatcher.ts` 的 `executeDispatch()` 完成后调用 `saveTaskHistory(task)` 持久化
- 历史记录需精简存储：不存文件内容，只存文件元数据 + 结果
- API 路由：`GET /api/dispatch/history`（分页+筛选）、`GET /api/dispatch/history/:id`（详情）
- 前端新增 `app/pages/ops/history/index.vue`
- 注意：暂存文件已被 cleanup 清理，"再次分发"需要提示用户重新上传文件

**优先级**：🔴 高（P0）— 现场必须能回看"上次分发了什么、哪些失败"，刷新即丢是硬伤

### 提议 3：实例间文件同步（Pull & Replicate）

**解决的痛点**

当前分发只能从本地磁盘上传文件。但在实际运维中，一个常见场景是"把 A 实例 bucket 里的某批文件同步到 B、C、D 实例"。用户不得不先把文件从 A 下载到本地，再上传到 miniops 暂存，最后分发——三步操作，大文件尤其痛苦。另一个场景是"从生产实例复制配置到新部署的实例"。

**功能描述**

新增"实例间同步"模式，与现有的"本地上传分发"并列：
- 选择**源实例 + 源 bucket + 前缀**，后端列出源对象列表
- 用户勾选要同步的对象（或全选）
- 选择**目标实例 + 目标 bucket**（与现有分发目标选择一致）
- 后端从源实例逐对象拉取 → 直接流式推送到目标实例（不落盘暂存磁盘）
- 同样走 SSE 进度推送，复用现有的进度聚合视图

**用户使用方式**

1. 分发页顶部新增模式切换：「本地上传」|「实例同步」
2. 选择「实例同步」后：
   - 选择源实例 → 选源 bucket → 输入前缀 → 后端列出匹配对象
   - 勾选要同步的对象
3. 下方"选择目标 & Bucket"区域与现有流程完全一致
4. 点击「开始同步」→ 进度视图与现有分发一致

**实现要点**

- 后端 `minio.ts` 新增 `getObjectStream()`（S3 GetObject，返回 ReadableStream）
- 新增 `uploadFromStream()`（复用 uploadSmall/uploadLarge 逻辑，但数据源从磁盘改为流）
- 源实例拉取 → 目标实例上传，使用管道流式传输，避免大文件占满内存
- dispatcher 新增 `executeSync()` 变体，任务类型扩展为 `dispatch | sync`
- API 路由：`POST /api/sync`（提交同步任务）、复用 `/api/dispatch/events` SSE
- 注意内存控制：流式传输时需限制并发，避免同时打开过多流

**优先级**：🔴 高（P0）— 替代"从 A 下载到本地再上传到 B"的三步低效操作，现场高频场景

### 提议 4：批量删除对象 ✅ 已实现

**解决的痛点**

当前平台只有"上传/分发"，没有"删除"。运维人员需要清理 MinIO 上的过期文件、错误分发的文件时，必须登录 MinIO Console 或用 mc 手动操作，无法批量、跨实例统一清理。特别是错误分发到几十个实例后，逐个登录删除非常低效。

**功能描述**

- 在对象浏览器（提议 1）中支持多选删除
- 在分发历史（提议 2）中，对失败的分发支持"清理已上传的部分"（回滚）
- 独立的"批量清理"入口：选择实例 + bucket + 前缀 → 列出对象 → 勾选删除
- 支持按前缀批量删除（删除某前缀下的所有对象）
- 删除前强制二次确认，显示即将删除的对象数量和总大小
- 删除结果同样走 SSE 进度推送

**用户使用方式**

1. 进入「批量清理」页面（或对象浏览器中的删除入口）
2. 选择目标实例 → 选 bucket → 输入前缀过滤
3. 预览匹配的对象列表（含大小、修改时间）
4. 全选或勾选要删除的对象
5. 点击「删除」→ 弹窗确认（显示对象数 + 总大小）→ 执行
6. 进度条展示删除进度，完成后显示成功/失败统计

**实现要点**

- S3 DeleteMultipleObjects API（单次最多 1000 个对象），需手写 SigV4 签名 + XML body
- 大批量删除自动分批（每 1000 个一批）
- API 路由：`POST /api/instances/objects/delete-batch`
- 复用 SSE 进度推送框架
- 安全性：删除操作需强制确认 + 记录审计日志（见提议 8）

**优先级**：🔴 高（P0）— 现场清理错误/过期文件是高频动作，与对象浏览器配套使用

**实现状态**：✅ 已实现（commit `467ef9f`）。跨实例批量清理页面 `/ops/cleanup`，支持多实例 + bucket + 前缀，SSE 实时进度推送。对象浏览器内单实例多选删除在提议 1 中已实现。分发失败回滚清理（④）依赖提议 2，后续实现。

### 提议 5：用户认证与访问控制

**解决的痛点**

当前 miniops 完全无认证，任何能访问到服务端口的人都可以：查看所有 MinIO 实例的 accessKey/secretKey、分发文件、删除实例配置。这在生产环境中是严重安全隐患。虽然 AGENTS.md 提到"密钥不进浏览器"，但密钥仍然明文存在 groups.json 中，且 API 完全无鉴权。

**功能描述**

- 简单的内置用户认证（用户名/密码），不依赖外部认证服务
- 登录页面 → Session Cookie（HttpOnly）维持登录态
- 默认单管理员账户，首次启动时通过环境变量设置初始密码
- 所有 API 路由（除登录接口）需校验登录态
- 可选：支持多用户 + 角色（管理员 / 操作员 / 只读），初期可只做单管理员
- 密码用 bcrypt 存储

**用户使用方式**

1. 首次部署时，通过环境变量 `MINIOPS_ADMIN_PASSWORD` 设置初始密码
2. 访问任意页面 → 未登录自动跳转登录页
3. 输入用户名（默认 admin）+ 密码 → 登录
4. 登录后可正常使用所有功能
5. 可在「设置」页面修改密码
6. 会话过期后需重新登录

**实现要点**

- 后端新增 `server/utils/auth.ts`：`hashPassword()`、`verifyPassword()`、`createSession()`、`requireAuth()` 中间件
- 使用 h3 的 `setCookie` / `getCookie` 管理 Session
- Session 存储初期用内存 Map（单实例部署），长期可迁移到文件/Redis
- 新增 `server/middleware/auth.ts`：Nitro 中间件拦截所有 `/api/` 路由（排除 `/api/auth/login`）
- API 路由：`POST /api/auth/login`、`POST /api/auth/logout`、`GET /api/auth/me`
- 前端新增 `app/pages/login.vue` + `app/middleware/auth.ts`（路由守卫）
- 密码哈希：用 `node:crypto` 的 scrypt（无需额外依赖）

**优先级**：🟡 中（P1）— 个人现场运维非第一优先级，但生产环境部署前必备

### 提议 6：密钥加密存储

**解决的痛点**

`groups.json` 中所有 MinIO 实例的 `accessKey` 和 `secretKey` 均明文存储。文件本身就是明文 JSON，任何有服务器文件系统访问权限的人都能直接看到所有 MinIO 凭据。AGENTS.md 也提到"含 MinIO 密钥，不要提交到公开仓库"，但即使不提交，服务器上的明文存储仍有风险。

**功能描述**

- 引入主密钥（Master Key），通过环境变量 `MINIOPS_MASTER_KEY` 配置
- 实例的 accessKey/secretKey 用 AES-256-GCM 加密后存储
- 读取时解密、写入时加密，对上层逻辑透明
- 提供迁移脚本：首次升级时自动将现有明文密钥加密
- groups.json 中密文字段加 `enc:` 前缀标识，兼容明文（迁移期）

**用户使用方式**

1. 部署时设置环境变量 `MINIOPS_MASTER_KEY`（32 字节随机字符串）
2. 首次启动时自动检测并加密现有明文密钥
3. 日常使用无感知——界面和 API 行为不变
4. 导出配置时可选择"导出明文"（需二次输入密码确认）或"导出密文"

**实现要点**

- `server/utils/crypto.ts`：`encrypt()` / `decrypt()`（AES-256-GCM，用 `node:crypto`）
- 修改 `store.ts` 的 `readRaw()` / `writeRaw()`：读时解密、写时加密
- 加密格式：`enc:<base64(iv + ciphertext + authTag)>`
- 向后兼容：读取时检测 `enc:` 前缀，无前缀视为明文（自动迁移）
- 主密钥缺失时：服务可启动但密钥相关操作报错提示配置
- 不引入新依赖，纯 `node:crypto` 实现

**优先级**：🟢 低（P2）— 安全加固，非现场即时需求

### 提议 7：分发预设/模板

**解决的痛点**

每次分发都要重复操作：选文件、展开实例组、勾选实例、逐个设 bucket、填前缀。对于"每周把同一批配置文件分发到同一组实例"这类重复性任务，每次都要从头来一遍。特别是 bucket 选择——如果实例较多，逐个设置非常繁琐。

**功能描述**

- 将当前分发页的配置（选中的实例、各实例的 bucket、目标前缀）保存为"预设"
- 预设可命名，如"1号线周配置分发"
- 分发页可一键加载预设，自动恢复实例选择和 bucket 配置
- 预设存储在后端（文件持久化），跨会话可用
- 支持预设的增删改查

**用户使用方式**

1. 在分发页配置好实例选择、bucket、前缀后
2. 点击「保存为预设」→ 输入名称 → 保存
3. 下次进入分发页，顶部出现「加载预设」下拉
4. 选择预设 → 自动勾选对应实例、填充 bucket 和前缀
5. 只需重新上传文件（或如果文件未过期，直接复用）即可快速分发
6. 在「设置」或预设管理页可编辑/删除已有预设

**实现要点**

- 存储到 `server/data/presets.json`，复用 store.ts 的互斥锁模式
- 数据结构：`{ id, name, instanceIds, instanceBuckets, prefix, createdAt }`
- API 路由：`GET/POST /api/presets`、`PUT/DELETE /api/presets/:id`
- 前端：分发页顶部增加预设选择器 + 保存按钮
- 注意：预设只保存"目标配置"，不含文件（文件暂存有 TTL 限制）

**优先级**：🟡 中（P1）— 减少重复配置，工作量小、即时收益明显

### 提议 8：操作审计日志

**解决的痛点**

当前系统无任何操作记录。谁删除了一个实例？谁向生产环境分发了文件？谁修改了实例配置？出了问题无法追责和排查。对于运维平台，操作审计是合规和运维治理的基本要求。

**功能描述**

- 记录所有关键操作：实例组 CRUD、实例 CRUD、分发任务提交、对象删除、配置导入/导出
- 每条日志含：时间、操作类型、操作者（需提议 5 的认证支持）、目标对象、操作详情、结果（成功/失败）
- 审计日志页面：按时间倒序、按操作类型/操作者筛选
- 日志持久化存储，可配置保留天数
- 初期可只记录不拦截，后续可扩展为关键操作需审批

**用户使用方式**

1. 左侧导航进入「审计日志」页面（仅管理员可见）
2. 按时间范围、操作类型、操作者筛选日志
3. 查看每条日志的详细信息
4. 可导出日志为 CSV/JSON（用于外部审计）

**实现要点**

- 存储方案：初期用 JSON 文件（按日期分文件），长期迁移 SQLite
- `server/utils/audit.ts`：`logAction(type, operator, target, detail, result)`
- 在所有关键 API 路由中调用 `logAction()`
- API 路由：`GET /api/audit-logs`（分页+筛选）
- 前端新增 `app/pages/audit/index.vue`
- 日志记录应异步执行，不阻塞主流程

**优先级**：🟢 低（P2）— 合规追溯，非现场即时需求，依赖认证才有操作者信息

### 提议 9：增量分发（跳过未变更文件）

**解决的痛点**

当前分发是"全量覆盖"模式——无论目标实例上是否已有相同文件，都会重新上传。对于"在 100 个实例上更新 1 个变了配置文件"的场景，99 个实例的无变化文件也被重新上传，浪费带宽和时间。特别是大文件场景，无意义的重复上传非常低效。

**功能描述**

- 分发时可选"跳过未变更文件"模式
- 判断逻辑：对比目标实例上已有对象的 ETag（MD5）与本地文件的 MD5，相同则跳过
- 对于 Multipart 上传的大文件，ETag 不是简单 MD5，需特殊处理（可用 Content-Length + Last-Modified 辅助判断）
- 跳过的文件在进度视图中标记为"已跳过"（独立状态，区别于成功/失败）
- 结果摘要增加"跳过 N 个"统计

**用户使用方式**

1. 分发页提交栏新增复选框「跳过未变更文件」
2. 勾选后，分发前后端先查询每个目标实例上对应对象的元数据
3. MD5 匹配的文件标记为"已跳过"，不实际上传
4. 进度视图中跳过的文件显示灰色"跳过"图标
5. 结果摘要：共 N 个，成功 X，跳过 Y，失败 Z

**实现要点**

- 后端 `minio.ts` 新增 `headObject()`（S3 HEAD 请求，获取对象元数据中的 ETag/Content-Length）
- 小文件（单次 PUT 上传）：ETag 即为 MD5，可直接对比
- 大文件（Multipart）：ETag 格式为 `<md5-of-part-md5s>-<partCount>`，需计算对比或改用 Content-Length + 自定义元数据
- dispatcher 在 `processInstance` 中增加前置检查逻辑
- DispatchResult 新增 `status: 'skipped'`
- 进度 SSE 事件和前端视图适配新状态

**优先级**：🟡 中（P1）— 重复分发提效：只传变化的文件，节省现场等待时间

### 提议 10：定时/计划分发任务

**解决的痛点**

某些分发需求是周期性的——例如"每天凌晨 2 点把最新配置分发到所有站点实例"。当前只能人工执行，无法设置定时任务。运维人员不得不设闹钟半夜起来手动分发，或写外部 cron 脚本绕过平台。

**功能描述**

- 创建定时分发任务：指定 Cron 表达式 + 分发配置（文件来源、目标实例、bucket、前缀）
- 文件来源支持两种：
  - 固定文件：从暂存目录中选取（需延长暂存 TTL 或引入"持久文件库"概念）
  - 源实例同步：从指定源实例拉取最新文件再分发（配合提议 3）
- 定时任务管理页：查看/暂停/启用/删除定时任务
- 每次执行自动记录到分发历史（配合提议 2）
- 执行失败时可选通知（邮件/Webhook，初期可只记日志）

**用户使用方式**

1. 进入「定时任务」页面，点击「新建任务」
2. 填写：任务名称、Cron 表达式、文件来源、目标实例、bucket、前缀
3. 保存后任务处于"启用"状态
4. 到达执行时间后自动触发，结果写入分发历史
5. 可在任务列表中暂停/启用/手动触发/删除

**实现要点**

- 后端新增 `server/utils/scheduler.ts`：基于 `setInterval` + Cron 表达式解析（可用 `node-cron` 或手写简易解析）
- 存储到 `server/data/schedules.json`
- Nitro plugin 启动时加载所有启用的定时任务并注册
- 注意：单实例部署下定时任务可靠；多实例需分布式锁（超出当前架构范围）
- 文件来源持久化问题：暂存文件有 TTL，定时任务需引用"持久文件库"或用源实例同步模式
- API 路由：`GET/POST /api/schedules`、`PUT/DELETE /api/schedules/:id`、`POST /api/schedules/:id/trigger`

**优先级**：🟢 低（P2）— 自动化能力，现场运维为人工场景，定时属进阶需求

### 提议 11：连通性测试增强（凭据验证） ✅ 已实现

**解决的痛点**

当前连通性测试只请求 `/minio/health/live`，该端点无需鉴权。测试"在线"只说明 MinIO 进程活着、网络可达，**不验证 accessKey/secretKey 是否正确**。用户配置完实例后以为"测试通过 = 配置正确"，到分发时才发现凭据错误，为时已晚。

**功能描述**

- 连通性测试升级为"连接性 + 凭据"双重验证
- 在现有 health/live 检查后，追加一次 ListBuckets 调用（需鉴权）
- 测试结果区分：
  - ✅ 在线 + 凭据有效
  - ⚠️ 在线但凭据无效（能连上 MinIO 但 ListBuckets 返回 403）
  - ❌ 不可达（网络不通 / 超时）
- 凭据无效时显示具体错误（如 "Access Denied"、"InvalidAccessKeyId"）

**用户使用方式**

1. 实例管理页点击「测试」→ 结果显示三级状态
2. 批量测试同样区分三级状态
3. 凭据无效的实例在列表中标红/标橙，提醒用户修正
4. 可选：分发前自动做凭据预检，凭据无效的实例提前标记失败

**实现要点**

- 修改 `minio.ts` 的 `testConnectivity()`：在 health/live 之后追加 `listBuckets()` 调用
- `ConnectivityResult` 新增 `authValid?: boolean` 字段
- 前端连通性列适配三级状态展示
- 可复用现有 `listBuckets()` 函数，无新增签名代码

**优先级**：🔴 高（P0）— 到现场第一步就能用：凭据错误会导致整个分发过程白跑

**实现状态**：✅ 已实现（commit `35222b1`）

改动文件：

| 文件 | 改动 |
|---|---|
| `server/utils/minio.ts` | `ConnectivityResult` 新增 `authValid` / `authError` 字段；`testConnectivity()` 在 health/live 通过后追加 `listBuckets()` 凭据验证；新增 `formatAuthError()` 格式化 403/401/超时错误 |
| `app/pages/groups/index.vue` | 接口同步；连通性列三态渲染（不可达红/凭据无效橙/在线绿）；组标题聚合 badge（N在线·M离线/凭据异常） |
| `app/pages/ops/dispatch/index.vue` | bucket 区域新增凭据警告图标（⚠️ + tooltip）；修复 `group.items[0]` 的 TS2532 类型错误 |
| `app/composables/useDispatch.ts` | `submit()` 新增凭据提醒 toast（不阻断提交） |

详细实施计划见 `docs/P0_IMPL_11_CONNECTIVITY.md`。

### 提议 12：暂存磁盘管理面板

**解决的痛点**

暂存文件存放在 `server/data/uploads/`，由 cleanup plugin 每 6 小时清理超过 TTL 的文件。但用户完全看不到暂存磁盘占用情况，不知道占了多少空间、有哪些残留文件。如果磁盘满了，上传直接失败但用户不知原因。管理员也无法手动触发清理或调整 TTL。

**功能描述**

- 系统设置页面展示暂存目录的磁盘使用情况：
  - 总占用空间
  - 暂存文件数量
  - 最老文件时间
  - 磁盘剩余空间
- 支持「立即清理」按钮，手动触发 cleanupExpired
- 支持查看暂存文件列表（文件名、大小、上传时间），可手动删除
- 可在线调整 `UPLOAD_TTL_HOURS`（持久化到配置文件，无需改环境变量重启）

**用户使用方式**

1. 进入「系统设置」→「暂存管理」
2. 查看磁盘占用仪表盘
3. 点击「立即清理」清除过期文件
4. 查看暂存文件列表，可手动删除单个/批量
5. 调整 TTL 天数（保存后生效）

**实现要点**

- 后端新增 `server/utils/system.ts`：`getDiskUsage()`、`getUploadStats()`
- API 路由：`GET /api/system/storage`、`POST /api/system/storage/cleanup`
- 前端新增 `app/pages/settings/index.vue` 或在现有页面增加 Tab
- `node:fs` 的 `statfs`（获取磁盘剩余空间）+ 递归 `readdir` + `stat`（计算占用）

**优先级**：🟡 中（P1）— 现场排障利器：磁盘满了能快速定位和清理，工作量小

## 四、技术约束与注意事项

1. **零 SDK 原则**：所有新增 S3 操作继续手写 SigV4 签名，不引入 AWS SDK，保持架构一致性。
2. **Nuxt UI 前缀**：所有新页面组件统一使用 `Nuxt` 前缀（`NuxtButton`、`NuxtTable` 等）。
3. **Node 兼容**：不使用 Bun 专有 API，全部使用 Node 标准库（`node:crypto`、`node:fs` 等）。
4. **数据存储**：初期继续用 JSON 文件 + 互斥锁模式，长期建议迁移 SQLite（`better-sqlite3`）以支持查询和并发。
5. **单实例假设**：当前架构基于单实例部署（内存任务表、内存 Session）。多实例部署需引入共享存储（Redis），属架构级变更。
6. **安全敏感操作**：删除、分发等操作需强制二次确认；密钥相关字段在 API 响应中需脱敏（当前已有 `[redacted]` 处理）。
7. **SSE 兼容**：新增的进度推送复用现有 `createEventStream` 框架；Nginx 反代需确保 `proxy_buffering off`。
