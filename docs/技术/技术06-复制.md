# 复制技术方案

> 依赖通用框架：`docs/技术/技术03-统一任务架构.md`
> 对应交互：`docs/交互/交互03-统一任务架构.md` §5

## 1. 概述

复制操作将对象从源 MinIO 实例/bucket 复制到目标实例/bucket。

**当前问题**：复制采用 SSE + IIFE 异步闭包模式，任务执行与 SSE 连接绑死，关闭页面或断线即中断，无法后台运行。

**改造目标**：改为 taskId 模式，任务由 TaskManager 管理执行，与连接解绑。提交后立即返回 taskId，进度通过通用 SSE 端点订阅，支持后台运行和断线重连。

**复制特点**：

- **无暂存阶段**：源数据在 MinIO 上，后端直接服务端复制或流式直传，不需要前端先上传到后端磁盘
- **提交即执行**：用户提交后立即进入执行队列，无需等待暂存
- **move 的基础**：移动 = 复制 + 删除源对象，MoveExecutor 内部复用 CopyExecutor 的复制逻辑（详见 `docs/技术/技术07-移动.md`）

## 2. 当前实现分析

### 2.1 copy.post.ts（SSE + IIFE）

当前 API 实现的核心模式：

```ts
// 1. 创建 SSE 流
const sse = createSSEStream(event)

// 2. IIFE 异步执行复制，不阻塞响应
;(async () => {
  // 收集 key -> 逐文件复制 -> 推送 SSE 事件
})()

// 3. 立即返回 SSE 流
return sse.response
```

**问题**：

- IIFE 闭包内的异步执行依赖 SSE 连接存活，连接断开则任务终止
- 任务状态全部在闭包内（success/failed 计数），无法从外部查询
- 无取消机制（`cancelRequested` 检查点不存在）
- 前端必须保持 `fetch + reader` 长连接读取 SSE

**当前 SSE 事件**：

| 事件 | 数据 | 说明 |
|------|------|------|
| `total` | `{ total: number }` | 扫描完成，推送对象总数 |
| `start` | `{ key: string }` | 单文件开始复制 |
| `progress` | `{ key, status, error? }` | 单文件复制结果 |
| `done` | `{ success, failed }` | 全部完成 |
| `error` | `{ message }` | 致命错误 |

**key 收集逻辑**（保留不变）：

```ts
const allKeys = new Set<string>(body.keys)
for (const prefix of body.prefixes) {
  const { keys, error } = await collectObjectsByPrefixes(
    sourceInstance, body.sourceBucket, [prefix]
  )
  if (error) { /* 推送 error 事件 */ return }
  for (const k of keys) allKeys.add(k)
}
```

**targetKey 计算逻辑**（保留不变）：

```ts
// 源前缀剥离后拼接到目标前缀下
const relativeKey =
  sourcePrefix && key.startsWith(sourcePrefix)
    ? key.slice(sourcePrefix.length)
    : key
const targetKey = targetPrefix
  ? `${targetPrefix.replace(/\/$/, '')}/${relativeKey}`
  : relativeKey
```

### 2.2 browse-copy-move-modal.vue（fetch + reader）

当前前端组件（copy 和 move 共用）的关键实现：

- **SSE 读取**：用 `fetch` POST 发起请求，通过 `res.body.getReader()` 流式读取 SSE 事件，手动解析 `event:` / `data:` 行
- **阶段**：`select -> scanning -> progress -> done`
  - `scanning`：POST 发起后等待 `total` 事件
  - `progress`：逐文件显示复制状态
  - `done`：显示汇总 + 失败重试
- **弹窗锁定**：执行期间 `:dismissible="false"` + `:close="!isRunning"`，弹窗不可关闭，无法后台运行
- **事件处理**：`handleSSEEvent(eventName, data)` 按 `total` / `start` / `progress` / `done` / `error` 分发

**问题**：

- `fetch + reader` 手动解析 SSE 比 `EventSource` 复杂且易错
- 执行期间弹窗锁定，用户被阻塞
- 无法断线重连（连接断开即任务终止）

## 3. CopyExecutor（server/utils/executors/copy.ts）

### 3.1 接口设计

CopyExecutor 实现 TaskExecutor 接口（见通用框架 §4），采用工厂函数模式，便于 move 复用：

```ts
import type { MinioInstance } from '#shared/schemas/groups'
import type { TaskExecutor } from '#server/utils/task-manager'

/** 复制参数（API 层查找实例后传入，executor 不依赖 store.ts） */
export interface CopyParams {
  sourceInstance: MinioInstance
  sourceBucket: string
  sourcePrefix: string
  keys: string[]
  prefixes: string[]
  targetInstance: MinioInstance
  targetBucket: string
  targetPrefix: string
}

/** 创建复制执行器 */
export function createCopyExecutor(params: CopyParams): TaskExecutor {
  return {
    async execute(task, emit, isCancelled) {
      // 见 §3.2
    },
  }
}
```

**为什么用工厂函数而非 class**：CopyExecutor 无状态（参数通过闭包捕获），工厂函数更简洁。MoveExecutor 可通过调用 `createCopyExecutor` 复用复制逻辑。

**为什么 params 传实例对象而非 ID**：实例查找（`getGroups` + `findInstance`）在 API 层完成，executor 只依赖 `minio.ts`，不依赖 `store.ts`，职责清晰。

### 3.2 执行流程

```
execute(task, emit, isCancelled):
  1. 收集所有 key
     ├─ keys 直接加入 allKeys（Set 去重）
     └─ 对每个 prefix 调 collectObjectsByPrefixes 递归展开
        ├─ 收集前检查 isCancelled()，取消则提前返回
        └─ 扫描失败 -> 抛异常（TaskManager 接管，emit error）

  2. 逐文件复制
     for (key of keyArray):
       ├─ 检查 isCancelled()，取消则 break
       ├─ emit progress { objectKey, result: { status: 'running' } }
       ├─ 计算 targetKey（源前缀剥离 + 拼接目标前缀）
       ├─ 推断 contentType = inferContentType(key)
       ├─ 调 copyObjectStream(source, ..., target, ..., targetKey, contentType)
       │   ├─ 同实例：CopyObjectCommand 服务端复制（快，不传文件内容）
       │   └─ 跨实例：GetObject -> Buffer -> PutObject 流式直传
       ├─ 成功：success++，emit progress { status: 'success', duration }
       └─ 失败：failed++，emit progress { status: 'failed', duration, error }
       （单文件失败不中断，继续下一个）

  3. 正常返回
     ├─ TaskManager 根据 cancelRequested 决定 emit complete 或 cancelled
     └─ summary 由 CopyExecutor 在执行结束前从 fileProgress 统计并写入 task.summary
```

**summary 统计**：CopyExecutor 在所有文件处理完毕后（return 前），从 `task.fileProgress.results` 统计：

```ts
const results = Object.values(task.fileProgress.results)
task.summary = {
  total: results.length,
  success: results.filter(r => r.status === 'success').length,
  failed: results.filter(r => r.status === 'failed').length,
  skipped: results.filter(r => r.status === 'skipped' || r.status === 'pending').length,
}
```

TaskManager 的 `processQueue` 读取 `task.summary` 推送 `complete`/`cancelled` 事件（若 executor 未设置则全零）。这与 DispatchExecutor 的模式一致（dispatch.ts 在执行结束前调用 `computeInstanceSummary` 设置 `task.summary`）。

### 3.3 取消检查点

取消检查点设在两个循环边界：

1. **prefix 收集循环**：每个 prefix 开始前检查 `isCancelled()`
2. **文件复制循环**：每个文件开始前检查 `isCancelled()`

```
取消时的行为：
  - 已复制的对象保留在目标（不回滚）
  - 未开始的对象跳过（fileProgress 中保持 pending）
  - TaskManager emit cancelled 事件，summary 包含 success/failed/skipped
```

**注意**：`collectObjectsByPrefixes` 内部的分页循环不插入取消检查点（收集通常很快），若某 prefix 下对象极多，收集过程不可中断。这是可接受的限制。

### 3.4 事件发射分工

CopyExecutor **只 emit `progress` 事件**（文件级进度），其余事件由 TaskManager 负责：

| 事件 | 由谁 emit | 时机 |
|------|----------|------|
| `queued` | TaskManager | 任务入队时 |
| `start` | TaskManager | 任务开始执行时 |
| `progress` | **CopyExecutor** | 每个文件开始/完成时 |
| `complete` | TaskManager | executor 正常返回且未取消 |
| `cancelled` | TaskManager | executor 返回且 cancelRequested=true |
| `error` | TaskManager | executor 抛异常时（message 取自异常） |

**致命错误处理**：扫描阶段（`collectObjectsByPrefixes`）失败时，executor 抛异常，TaskManager 捕获后 emit `error` 事件。executor 不自行 emit error。

**单文件失败不致命**：单个文件复制失败只 emit `progress { status: 'failed' }`，继续复制后续文件。任务最终状态为 `done`（非 `failed`），summary 中 `failed > 0`。

### 3.5 targetKey 计算函数

提取为独立导出函数，供 MoveExecutor 复用：

```ts
/**
 * 计算复制后的目标 key：源前缀剥离后拼接到目标前缀下。
 * 例：sourcePrefix='data/', key='data/a/b.txt', targetPrefix='backup'
 *     -> relativeKey='a/b.txt' -> targetKey='backup/a/b.txt'
 */
export function computeTargetKey(
  sourcePrefix: string,
  key: string,
  targetPrefix: string,
): string {
  const relativeKey =
    sourcePrefix && key.startsWith(sourcePrefix)
      ? key.slice(sourcePrefix.length)
      : key
  return targetPrefix
    ? `${targetPrefix.replace(/\/$/, '')}/${relativeKey}`
    : relativeKey
}
```

## 4. API 改造

### POST /api/browse/objects/copy

**请求体**：不变（与当前一致）

```ts
{
  sourceInstanceId: string
  sourceBucket: string
  sourcePrefix: string
  keys: string[]
  prefixes: string[]
  targetInstanceId: string
  targetBucket: string
  targetPrefix: string
}
```

**响应**：从 SSE 流改为 JSON

```ts
// 旧：返回 SSE 流（text/event-stream）
// 新：返回 JSON
{ taskId: string }
```

**改造后实现**：

```ts
export default defineEventHandler(async (event) => {
  const body = await readBody<CopyRequestBody>(event)

  // 1. 参数校验（不变）
  // 2. 查找源/目标实例（不变，getGroups + findInstance）

  // 3. 构造任务描述
  const description: TaskDescription = {
    type: 'copy',
    label: `复制 ${body.keys.length} 个对象` +
      (body.prefixes.length > 0 ? ` + ${body.prefixes.length} 个文件夹` : ''),
    detail: `${sourceInstance.name}/${body.sourceBucket} -> ${targetInstance.name}/${body.targetBucket}`,
  }

  // 4. 创建执行器（工厂函数，闭包捕获参数）
  const executor = createCopyExecutor({
    sourceInstance,
    sourceBucket: body.sourceBucket,
    sourcePrefix: body.sourcePrefix,
    keys: body.keys,
    prefixes: body.prefixes,
    targetInstance,
    targetBucket: body.targetBucket,
    targetPrefix: body.targetPrefix,
  })

  // 5. 创建任务，返回 taskId
  const taskId = createTask(description, executor)

  // 6. 返回 JSON（不再返回 SSE 流）
  return { taskId }
})
```

**变化要点**：

- 移除 `createSSEStream` 和 IIFE 闭包
- 移除 `collectObjectsByPrefixes` / `copyObjectStream` / `inferContentType` 的直接调用（移入 CopyExecutor）
- SSE 订阅改由通用端点 `GET /api/tasks/:taskId/events` 承担
- 实例查找逻辑保留在 API 层（executor 不依赖 store.ts）

## 5. 前端改造

### 5.1 改造要点

`browse-copy-move-modal.vue` 是 copy 和 move 共用组件。本文档描述 copy 部分的改造，move 特有的删源阶段（`phase` 事件、删除进度）详见 `docs/技术/技术07-移动.md`。

**移除**：

- `fetch` + `res.body.getReader()` 流式读取 SSE 的全部代码
- 手动解析 `event:` / `data:` 行的逻辑
- `handleSSEEvent` 中按旧事件名（`total` / `start` / `progress` / `done` / `error`）分发的逻辑

**新增**：

- POST 提交获取 taskId
- 调用 `useTaskManager().subscribeTask(taskId)` 订阅进度
- 按 `TaskEvent` 统一事件更新 UI
- "后台继续"按钮（关闭弹窗，任务在后端继续）

### 5.2 事件映射

| 旧事件 | 新 TaskEvent | 前端处理 |
|--------|-------------|---------|
| `total { total }` | （无对应事件） | 复制无暂存阶段，扫描在 executor 内部完成，执行中不推送总数。前端只显示文件列表（✅/❌/⏳），不显示 N/M 进度条；完成后 `summary.total` 为总数 |
| `start { key }` | `progress { objectKey, result: { status: 'running' } }` | 标记文件进行中 |
| `progress { key, status, error }` | `progress { objectKey, result: { status, error, duration } }` | 更新文件状态 |
| `done { success, failed }` | `complete { summary }` | 任务完成，显示汇总 |
| `error { message }` | `error { message }` | 任务失败 |
| — | `queued { queuePosition }` | 显示排队中 + 队列位置 |
| — | `start { taskId }` | 任务开始执行，切换到执行中 |
| — | `cancelled { summary }` | 任务已取消，显示汇总 |

### 5.3 阶段调整

```
旧：select -> scanning -> progress -> done
新：select -> progress -> done
```

- **移除 `scanning`**：扫描（收集 key）在 CopyExecutor 内部完成，前端通过 `progress` 事件感知。收到第一个 `progress` 事件即进入执行中状态
- **`progress` 内部区分**：
  - 收到 `queued` 事件 → 显示"排队中（第 N 位）"
  - 收到 `start` 事件 → 显示"执行中"
  - 收到 `progress` 事件 → 更新文件列表
- **POST 请求期间**：按钮 loading 态，不切换 phase（仍在 `select`，请求成功后才切 `progress`）

### 5.4 提交流程改造

```ts
async function startTransfer() {
  const body = { /* 同当前，sourceInstanceId/keys/prefixes/target... */ }

  // 旧：fetch POST + reader 读取 SSE 流
  // 新：POST 提交获取 taskId
  const { taskId } = await $fetch<{ taskId: string }>(
    `/api/browse/objects/${props.mode}`,
    { method: 'POST', body }
  )

  // 订阅任务进度（useTaskManager 内部创建 EventSource）
  currentTaskId.value = taskId
  phase.value = 'progress'
  await useTaskManager().subscribeTask(taskId)
}
```

**进度数据来源**：从 `useTaskManager` 的全局任务状态获取，按 `taskId` 匹配当前任务：

```ts
const currentTask = computed(() => {
  // 从 activeTask / queueTasks / completedTasks 中找匹配 taskId 的
  const tm = useTaskManager()
  return tm.activeTask.value?.taskId === currentTaskId.value
    ? tm.activeTask.value
    : tm.queueTasks.value.find(t => t.taskId === currentTaskId.value)
    ?? tm.completedTasks.value.find(t => t.taskId === currentTaskId.value)
    ?? null
})

// 文件列表从 fileProgress.results 渲染
const progressItems = computed(() => {
  const results = currentTask.value?.fileProgress?.results ?? {}
  return Object.entries(results).map(([key, result]) => ({
    key,
    name: key.split('/').pop() ?? key,
    status: result.status,
    error: result.error,
    duration: result.duration,
  }))
})
```

### 5.5 后台继续

当前组件执行期间弹窗锁定（`:dismissible="false"`, `:close="!isRunning"`）。改造后：

- 执行阶段弹窗可关闭（移除 `dismissible=false`）
- 新增"后台继续"按钮，点击后关闭弹窗，任务在后端继续
- 任务状态由 `useTaskManager` 全局维护，关闭弹窗不影响

```ts
function background() {
  // 关闭弹窗，任务继续在后端执行

```

**恢复进度**：重新打开弹窗时，若 `currentTaskId` 对应的任务仍在进行中，从 `useTaskManager` 获取当前状态恢复进度视图（若已不在内存中则从 `GET /api/tasks/:taskId/state` 拉取）。

### 5.6 完成处理

| 场景 | 来源事件 | UI |
|------|---------|-----|
| 全部成功 | `complete { summary: { failed: 0 } }` | toast 提示 + 刷新对象列表 |
| 有失败 | `complete { summary: { failed > 0 } }` | 弹窗显示失败项 + 重试按钮 |
| 已取消 | `cancelled { summary }` | 显示已取消 + 已完成汇总 |

## 8. 风险

### 跨实例大文件内存占用

`copyObjectStream` 跨实例时将文件缓冲成 Buffer 再上传（AWS SDK v3 对 Node Readable stream 默认用 chunked transfer encoding，旧版 MinIO 不支持）。单文件内存占用 = 文件大小。

串行执行（一次只复制一个文件）限制了并发内存占用，但单个超大文件仍可能占用较多内存。这是 `copyObjectStream` 的既有行为，本次改造不改变。

### 同名对象覆盖

MinIO PUT / CopyObject 是覆盖语义，复制同名对象直接覆盖，不弹确认（与当前行为一致，交互文档 §9.4）。

### 源前缀与 key 不匹配

若 `key` 不以 `sourcePrefix` 开头（用户手动选了前缀外的对象），`computeTargetKey` 会保留完整 key 拼接到目标前缀下。这是当前行为的保留，不改变。
