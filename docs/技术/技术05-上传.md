# 上传技术方案

> 依赖通用框架：`docs/技术/技术03-统一任务架构.md`（TaskManager / 暂存管理 / SSE / useTaskManager / TaskViewerButton）
>
> 对应交互：`docs/交互/交互03-统一任务架构.md` §4 上传交互

## 1. 概述

实例访问页的上传当前是**同步转发**模型：前端 XHR 把文件 multipart 发给后端，后端 `await uploadObjectStream` 同步写 MinIO，整个传输绑死在单次 HTTP 请求生命周期上--关页面即中断，且 `arrayBuffer` 全量进内存。

本方案将上传改为**两阶段**：

- **暂存**：前端 XHR 逐文件把文件写到后端磁盘（`staging.stageFile()` 流式落盘，不进内存）。
- **后端异步上传**：提交任务后由 `UploadExecutor` 从磁盘流式读取上传到目标 MinIO，走 TaskManager 队列，与 SSE 连接解绑。

**upload 与 dispatch 的关系**：上传本质是"单实例分发"--暂存到同一磁盘目录，上传时目标实例 = 1。因此 `UploadExecutor` **复用 DispatchExecutor 的上传实现**（readFile 读磁盘 + 单次 PUT、取消检查点、清理暂存），区别仅在于：

| 维度 | DispatchExecutor | UploadExecutor |
| --- | --- | --- |
| 目标实例数 | N（实例维度并发） | 1（无并发，文件串行） |
| 进度结构 | `InstanceProgress[]`（实例维度矩阵） | `FlatFileProgress`（扁平文件结果） |
| 目标来源 | 分发页实例树勾选 | 实例访问页当前浏览的 instance + bucket + prefix |
| 入口 | 分发页 | 实例访问页对象浏览器工具栏 |

> **实施决策（2026-08 评审时拍板）**：
> 1. 上传策略与 dispatch **现状**对齐：`readFile` Buffer + `uploadObjectStream` 单次 PUT，不引入 Multipart Upload 与 `object-upload.ts` 共享模块。原稿"小文件 PUT / ≥8MB Multipart / object-upload.ts"引用的是模板重置（269671c）前已废弃的 V2 代码，dispatch 重写（864e842）时未搬过来；待真实出现大文件需求时再为 dispatch + upload 一并升级。
> 2. 暂存沿用 `stageFile(Buffer)` 全量落盘（与 dispatch/stage 一致）：暂存内存占用 = 单文件大小，前端逐文件串行上传，可接受。原稿"流式落盘不进内存"从未实现，此处纠正。

## 2. 当前实现分析

### 2.1 后端 `server/api/browse/objects/upload.post.ts`

同步转发，绑请求：

```ts
// 全量读进内存（SDK 无法对 Web ReadableStream 计算 checksum）
const body = new Uint8Array(await file.arrayBuffer())
await uploadObjectStream(instance, bucket, objectKey, body, contentType, file.size)
return { key: objectKey, size: file.size }
```

问题：

- **绑请求**：`await` 阻塞在请求生命周期内，关页面即中断，无后台能力。
- **全量进内存**：`file.arrayBuffer()` 把整个文件读成 `Uint8Array`，大文件内存压力大（与通用框架"流式不落盘内存"目标冲突）。
- **无任务化**：不进 TaskManager 队列，任务查看器不可见，无 SSE 进度，无重连恢复。
- **无暂存**：前端 XHR 直传 MinIO，后端不落盘。

### 2.2 前端 `app/components/browse-upload-modal.vue`

XHR 直传，三阶段：

| 项 | 当前实现 | 位置 |
| --- | --- | --- |
| phase | `select -> uploading -> done` | `:38` |
| 上传方式 | `XMLHttpRequest` 直传 `/api/browse/objects/upload`，`FormData` 带单文件 | `:144-186` |
| 进度 | `xhr.upload.onprogress` 真实百分比，逐文件串行 | `:157-161` |
| 弹窗关闭 | `:dismissible="false"`，uploading 阶段不可关 | `:232` |
| 取消 | `xhr.abort()` 中止当前请求，已上传不回滚 | `:199-211` |
| 完成 | toast + `emit('complete')` 刷新列表 | `:213-218` |

问题：上传阶段绑弹窗（`:dismissible=false`），不可后台继续；无任务化，无 SSE，进度仅弹窗内可见。

## 3. UploadExecutor（server/utils/executors/upload.ts）

实现 `TaskExecutor` 接口（通用框架 §4）：

```ts
interface TaskExecutor {
  execute(task: Task, emit: (event: TaskEvent) => void, isCancelled: () => boolean): Promise<void>
}
```

### 3.1 接口与构造

```ts
import type { TaskExecutor } from '#shared/schemas/task'
import type { TaskEvent, FlatFileProgress, FileResult } from '#shared/schemas/task'

/** 上传任务参数（由 POST /api/browse/objects/upload 构造后传入） */
export interface UploadParams {
  files: { fileId: string; objectKey: string }[]  // 已暂存的文件 + 落盘 objectKey
  target: { instanceId: string; instanceName: string; bucket: string }
  prefix: string                                    // 目标前缀（已由后端 sanitizeObjectKey 清洗）
}

export function createUploadExecutor(params: UploadParams): TaskExecutor
```

> 与 DispatchExecutor 一致，「每任务一个实例」--闭包捕获参数，返回的 `TaskExecutor` 注册到 `TaskManager.createTask()`，任务结束后丢弃。

### 3.2 execute 方法逻辑

```ts
async execute(task, emit, isCancelled) {
  const stagedFiles = getStagedFiles(params.files.map(f => f.fileId))

  // 1. 初始化扁平进度 fileProgress.results
  //    预填所有 objectKey = { status: 'pending' }
  // 2. 同步到 task.fileProgress（供 SSE 快照重连恢复）

  emit({ event: 'start', data: { taskId: task.taskId } })

  const instance = getInstanceById(params.target.instanceId)   // 从 store 读取 MinioInstance

  // 3. 文件串行上传（单实例，无并发）
  for (const f of stagedFiles) {
    // 取消检查点：每文件开始前检查
    if (isCancelled()) {
      markRemainingSkipped(f.objectKey)                         // 未开始的标记 skipped
      break
    }

    const fullKey = buildFullKey(params.prefix, f.objectKey)    // prefix/objectKey
    const contentType = inferContentType(f.originalName)        // 显式 Content-Type

    // 标记 running，emit progress（无 instanceId 字段，扁平结构）
    setResult(f.objectKey, { status: 'running' })
    emit({ event: 'progress', data: { taskId: task.taskId, objectKey: f.objectKey, result: { status: 'running' } } })

    const start = Date.now()
    try {
      // 与 DispatchExecutor 一致：readFile 全量读 + 单次 PUT
      const body = await readFile(f.diskPath)
      await uploadObjectStream(instance, params.target.bucket, fullKey, body, contentType, f.size)
      setResult(f.objectKey, { status: 'success', duration: Date.now() - start })
    } catch (e) {
      setResult(f.objectKey, { status: 'failed', error: formatError(e), duration: Date.now() - start })
    }
    emitProgressDone(f.objectKey)   // 成功/失败都 emit，前端更新扁平列表
  }

  // 4. 汇总 summary（total = files.length）
  //    走取消分支时按 cancelRequested 设置 task.status，由 TaskManager 决定 done/cancelled

  // 5. 清理暂存文件（上传完成后无论成功失败都清理磁盘）
  await Promise.all(stagedFiles.map(f => removeStagedFile(f.fileId)))
}
```

### 3.3 上传实现与 DispatchExecutor 一致

与 dispatch.ts 的上传循环同构：`readFile(f.diskPath)` 读磁盘 Buffer -> `minio.ts:uploadObjectStream()` 单次 PUT -> `inferContentType()` 推断 Content-Type -> 单文件失败不中断，继续下一个。不引入 Multipart Upload 与 `object-upload.ts` 共享模块（见 §1 实施决策）。

### 3.4 FlatFileProgress（扁平文件进度）

UploadExecutor 用 `FlatFileProgress` 维护进度（通用框架 §3），区别于 DispatchExecutor 的 `InstanceProgress[]`：

```ts
// task.fileProgress 结构
{
  results: {
    'config.json':  { status: 'success', duration: 320 },
    'logo.png':     { status: 'failed', error: '403 Access Denied', duration: 120 },
    'sub/data.yaml': { status: 'pending' },
  }
}
```

- 每次 `setResult` 更新 `task.fileProgress.results[key]`，同时 `emit('progress', { taskId, objectKey, result })`（**不带 `instanceId`**，扁平结构无需定位实例行）。
- 该结构也用于 SSE 重连恢复：前端断线后 `GET /api/tasks/:taskId/state` 返回含 `fileProgress` 的快照，重建扁平列表。

### 3.5 取消检查点

通用框架 `cancelTask()` 设置 `cancelRequested = true`，`isCancelled()` 回调读取它。UploadExecutor 在每文件开始前检查：

**每文件开始前**：`if (isCancelled()) { markRemainingSkipped(f.objectKey); break }`--未开始的文件标记 `skipped`，与 `failed` 区分。正在传输的文件会完成当前 PUT（无分片中断点，取消在下一文件边界生效）。

> 已完成上传的文件保留在目标实例（不回滚），符合交互 §4。

### 3.6 完成后清理暂存文件

`execute()` 末尾 `Promise.all(stagedFiles.map(f => removeStagedFile(f.fileId)))` 删除磁盘暂存文件。无论任务成功/失败/取消都执行（try-finally）。孤儿清理（`cleanupOrphanedFiles`）兜底处理进程重启等异常残留。与 DispatchExecutor 行为一致（技术04 §2.7）。

## 4. API 改造

### 4.1 暂存接口 POST /api/browse/objects/stage

`multipart/form-data`，逐文件调用。前端 XHR 流式上传，落盘到暂存目录。**复用通用框架 `staging.ts`**，与 `POST /api/dispatch/stage`（技术04 §3.1）实现一致，均为薄路由。

```ts
// server/api/browse/objects/stage.post.ts
export default defineEventHandler(async (event) => {
  const form = await readMultipartFormData(event)
  const file = form?.find(f => f.name === 'file')        // 单文件字段
  const objectKey = form?.find(f => f.name === 'objectKey')?.data.toString('utf8')

  // 1. 校验 MAX_UPLOAD_SIZE
  // 2. sanitizeObjectKey(objectKey) 清洗路径
  // 3. stageFile(stream, objectKey, file.filename, inferContentType(objectKey)) 流式落盘
  //    注意：不要用 file.type 作为 Content-Type——Bun 运行时 formData() 会给
  //    multipart part 的 Content-Type 追加 ;charset=utf-8（Node/undici 无此行为），
  //    原样写入 MinIO 后会导致 Console 无法预览（同 dispatch/stage 的坑）
  //    （file.filepath 转 ReadableStream，或直接用 Node stream 写盘）
  // 4. 返回 { fileId }
  return { fileId: stagedFile.fileId }
})
```

| 项 | 说明 |
| --- | --- |
| 请求体 | `multipart/form-data`：`file`（文件）+ `objectKey`（落盘 key，文件夹内文件带相对路径） |
| 返回 | `{ fileId: string }` |
| 大小限制 | `MAX_UPLOAD_SIZE`（默认 0=不限），超限返回 413 |
| 路径安全 | `sanitizeObjectKey` 防路径遍历 |
| 底层复用 | `staging.stageFile()`（通用框架 §5），与 dispatch/stage 共用同一暂存目录与内存 Map |

> **为何独立路由而非复用 `/api/dispatch/stage`**：上传是实例访问页（对象浏览器）的操作，路由放在 `objects/` 资源下符合 RESTful 组织，且避免上传依赖 dispatch 模块路径。两者均为薄路由，核心逻辑全部下沉到 `staging.ts`，无重复代码。

> 暂存路由**不创建 TaskManager 任务**，不进执行队列（暂存不排队，交互 §7.4）。它只是把文件写到磁盘并登记到 `staging.ts` 的内存 Map。

### 4.2 提交接口 POST /api/browse/objects/upload

改造现有 `upload.post.ts`：从同步转发改为创建任务并返回 `taskId`。提交时所有文件已暂存完成。

```ts
// server/api/browse/objects/upload.post.ts
export default defineEventHandler(async (event) => {
  const body = await readBody(event)
  // body: { files: { fileId, objectKey }[], instanceId, bucket, prefix }

  // 1. 校验：files 非空、instanceId/bucket 存在、fileId 均已暂存（getStagedFiles）
  // 2. 从 store 查实例 -> instanceName
  // 3. prefix 经 sanitizeObjectKey 清洗
  // 4. createUploadExecutor(params) -> createTask(description, executor) -> 返回 taskId
  return { taskId }
})
```

**请求体**（从 multipart 改为 JSON，因文件已暂存，只传 fileId 引用）：

```ts
{
  files: { fileId: string; objectKey: string }[]
  instanceId: string
  bucket: string
  prefix: string
}
```

- `files`：暂存阶段逐文件拿到的 `fileId` + 前端计算的 `objectKey`（单文件=文件名，文件夹内=相对路径）。
- `instanceId` / `bucket` / `prefix`：实例访问页当前浏览上下文。最终 key = `prefix/objectKey` 由后端拼接。

**返回**：`{ taskId: string }`（不再返回 `{ key, size }`）

**任务描述**（任务查看器展示）：

```ts
{
  type: 'upload',
  label: `上传 ${files.length} 个文件`,
  detail: `${instanceName} / ${bucket}${prefix ? ' / ' + prefix : ''}`
}
```

> 原 `upload.post.ts` 的 multipart 同步转发逻辑整体删除（参数校验、实例查询、objectKey 构造迁移到提交接口 + UploadExecutor）。

### 5.2 暂存阶段（staging）

- XHR 逐文件调 `POST /api/browse/objects/stage`（`multipart/form-data`），用 `XMLHttpRequest` 而非 `$fetch`，因需要 `upload.onprogress` 回调拿上传百分比（沿用现有 `uploadSingleFile` 的 XHR 模式，仅改 URL 与返回处理）。
- 每文件暂存完成存 `fileId`，失败标记 ❌ + 错误信息，不影响其他文件。
- 进度展示：扁平文件列表 + 每行上传进度条 + 百分比（沿用现有 uploading 视图的进度条样式）。
- **弹窗不可关闭**（`:dismissible=false`）：暂存是前端 XHR，关闭/离开即中断。
- **取消**：`xhr.abort()` 未完成请求，回到 select，已暂存文件由后端 TTL 清理。

```ts
// 伪代码：暂存单文件
function stageSingleFile(item: UploadItem): Promise<{ fileId: string }> {
  return new Promise((resolve, reject) => {
    const formData = new FormData()
    formData.append('objectKey', item.relativePath)   // 文件夹内文件带相对路径
    formData.append('file', item.file, item.name)
    const xhr = new XMLHttpRequest()
    currentXhr = xhr
    xhr.upload.addEventListener('progress', (e) => {
      if (e.lengthComputable) item.progress = (e.loaded / e.total) * 100
    })
    xhr.addEventListener('load', () => {
      if (xhr.status >= 200 && xhr.status < 300) resolve(JSON.parse(xhr.responseText))
      else reject(new Error(parseError(xhr)))
    })
    xhr.addEventListener('error', () => reject(new Error('网络错误')))
    xhr.addEventListener('abort', () => reject(new Error('已取消')))
    xhr.open('POST', '/api/browse/objects/stage')
    xhr.send(formData)
  }).finally(() => { currentXhr = null })
}
```

### 5.3 上传阶段（uploading）

- 全部暂存成功后，`POST /api/browse/objects/upload` 提交（传 `files`/`instanceId`/`bucket`/`prefix`），拿 `taskId`。
- `useTaskManager().subscribeTask(taskId)` 订阅 SSE：先 `GET /api/tasks/:taskId/state` 拿快照重建 `fileProgress` 扁平列表，再 `EventSource` 接收增量 `progress` 事件更新列表。
- 进度展示：扁平文件列表，每行 文件名 + 大小 + 状态（✅ 成功附耗时 / ❌ 失败附错误 tooltip / ⏳ 上传中 / ⬜ 等待中）。
- **弹窗可关闭**（「后台继续」）：点击后关闭弹窗，任务在后端继续，navbar 任务查看器全局可见。
- **取消上传**：`useTaskManager().cancelTask(taskId)` -> `POST /api/tasks/:taskId/cancel`，后端设 `cancelRequested`，执行器在检查点停止。

```ts
// 伪代码：暂存完成 -> 提交 -> 订阅
async function startUpload() {
  phase.value = 'staging'
  // 1. 逐文件暂存，收集 fileId
  const files = []
  for (const item of items.value) {
    const { fileId } = await stageSingleFile(item)
    files.push({ fileId, objectKey: item.relativePath })
  }
  // 2. 提交上传任务
  phase.value = 'uploading'
  const { taskId } = await $fetch('/api/browse/objects/upload', {
    method: 'POST', body: { files, instanceId, bucket, prefix }
  })
  // 3. 订阅 SSE（useTaskManager 内部处理重连）
  const { subscribeTask } = useTaskManager()
  await subscribeTask(taskId)
  // progress 事件驱动 items 状态更新
}
```

### 5.4 上传完成

- 全部成功：toast 提示 + `emit('complete')` 刷新对象列表；弹窗显示 ✅。
- 有失败：弹窗内显示失败项 + 错误信息，失败行显示「重试失败项」按钮。
- 已取消：弹窗显示 ⊘，未完成文件标记"已跳过"。

**重试失败项**：从 `fileProgress` 提取 `status==='failed'` 的 objectKey，重新选文件 -> staging -> 提交（新 taskId）。因上次暂存文件已被清理，重试需重新走暂存阶段。

### 5.5 后台继续

- 点击「后台继续」关闭弹窗，任务在后端继续。
- navbar 任务查看器入口显示执行中状态（旋转图标 + 角标）。
- 重新打开上传弹窗时不恢复进度（通过任务查看器查看），弹窗回到 select 初始态。
