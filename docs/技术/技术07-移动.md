# 移动技术方案

> 依赖通用框架：`docs/技术/技术03-统一任务架构.md`
> 对应交互：`docs/交互/交互03-统一任务架构.md` §6

## 1. 概述

移动 = 复制 + 删除源对象（两阶段操作）。当前实现与 copy 同为 SSE + IIFE 模式（任务绑死连接、关闭页面即中断），改为基于通用框架的 taskId 模式：后端创建任务后独立执行，断线不中断、重连可恢复、可后台运行。

移动相对复制多一个"删除源对象"阶段，通过 `phase` 事件 + `currentPhase` 字段驱动前后端阶段切换。复制阶段逻辑尽量复用 CopyExecutor，删除阶段复用 `deleteObjects`。

## 2. 当前实现分析

### 2.1 move.post.ts

- 模式：`createSSEStream` + IIFE（`;(async () => {...})()`），任务执行绑死 SSE 连接，断连即终止
- 两阶段：
  1. 收集 key（`collectObjectsByPrefixes`）+ 逐个复制（`copyObjectStream`）
  2. 批量删除已成功复制的源对象（`deleteObjects`）
- 事件：`total` / `start` / `progress` / `deleting` / `source-deleted` / `done` / `error`
- 删除阶段用 `deleteObjects` 一次性批量删除（S3 DeleteMultipleObjects，内部自动分批每 1000 个），返回 `deleted[]` + `errors[]` 后逐个发 `source-deleted` 事件
- 目标 key 计算：源前缀剥离后拼接到目标前缀下（与 copy 完全一致）

### 2.2 browse-copy-move-modal.vue

- 与 copy 共用同一组件，`mode: 'copy' | 'move'` 区分
- 进度通过 `fetch + reader` 流式读取 POST SSE（EventSource 只支持 GET，故用 fetch）
- 执行期间弹窗 `:dismissible=false` 不可关闭
- move 专属 UI：每个文件项除复制状态外，额外展示删源状态（`sourceDeleted: 'deleted' | 'delete-failed'`）；进度区有"正在删除源对象..."提示
- 完成汇总含 `sourceDeleted` / `sourceDeleteFailed` 计数

### 2.3 改造要点

| 维度 | 当前 | 改造后 |
|------|------|--------|
| 执行模型 | SSE + IIFE，绑连接 | taskId，后端独立执行 |
| 连接断开 | 任务终止 | 不影响，重连恢复 |
| 进度推送 | POST SSE（fetch reader） | GET SSE（EventSource，通用 `/api/tasks/:taskId/events`） |
| 关闭弹窗 | 执行中不可关 | 执行中可"后台继续"，任务继续 |
| 阶段切换 | `deleting` 事件 | `phase` 事件 + `currentPhase` 字段 |

## 3. MoveExecutor（server/utils/executors/move.ts）

### 3.1 设计概要

MoveExecutor 实现通用框架的 `TaskExecutor` 接口，分两阶段执行：

```
阶段 1 copying：收集 key + 逐个复制（复用 CopyExecutor 逻辑）
   ↓ phase 事件 { phase: 'copying' }
   逐文件复制，fileProgress 记录复制结果
   ↓ phase 事件 { phase: 'deleting' }
阶段 2 deleting：批量删除已成功复制的源对象
   ↓
完成，计算 summary
```

- 用扁平 `FlatFileProgress`（`results: Record<objectKey, FileResult>`）记录每个对象的状态
- 用 `currentPhase`（`'copying' | 'deleting'`）记录当前阶段，通过 `phase` 事件通知前端切换 UI
- 执行器作为闭包创建，捕获请求参数（源/目标实例、keys、prefixes 等），无需在 Task 上新增 params 字段

### 3.2 复用 CopyExecutor 的复制逻辑

复制阶段与 CopyExecutor 完全一致（收集 key、计算目标 key、`copyObjectStream` 逐个复制、发 progress 事件）。为避免重复，建议在 `server/utils/executors/copy.ts`（CopyExecutor 所在文件）抽出一个共享函数，供 CopyExecutor 和 MoveExecutor 复用：

```ts
/**
 * 复制阶段：收集 key + 逐个复制，更新 fileProgress 并发 progress 事件。
 * 被 CopyExecutor 和 MoveExecutor 复用。
 *
 * @returns 成功复制的 key 列表（供 move 的删除阶段使用）
 */
export async function copyObjectsPhase(
  task: Task,
  emit: (event: TaskEvent) => void,
  isCancelled: () => boolean,
  params: {
    sourceInstance: MinioInstance
    sourceBucket: string
    sourcePrefix: string
    keys: string[]
    prefixes: string[]
    targetInstance: MinioInstance
    targetBucket: string
    targetPrefix: string
  },
): Promise<string[]>  // copiedKeys
```

MoveExecutor 阶段 1 直接调用 `copyObjectsPhase`，阶段 2 用返回的 `copiedKeys` 调 `deleteObjects`。

### 3.3 FileResult 扩展（move 专属）

通用框架的 `FileResult` 只有 `status` / `duration` / `error`，无法同时表达"复制结果"和"删除源结果"。移动需要保留复制成功状态的同时记录删除结果，因此对 `shared/schemas/task.ts` 的 `FileResult` 增加两个可选字段（move 专属，copy/upload/dispatch 不设置，无影响）：

```ts
export interface FileResult {
  status: 'success' | 'failed' | 'running' | 'pending' | 'skipped'
  duration?: number
  error?: string
  // —— move 专属 ——
  sourceDeleteStatus?: 'deleted' | 'delete-failed'  // 删除源结果（仅 move 的 deleting 阶段设置）
  sourceDeleteError?: string                          // 删除源失败错误
}
```

字段语义：

| `sourceDeleteStatus` | 含义 |
|----------------------|------|
| `undefined` | 未进入删除阶段，或该对象复制未成功不参与删除 |
| `'deleted'` | 源对象已成功删除 |
| `'delete-failed'` | 源对象删除失败（配合 `sourceDeleteError`） |

复制阶段的 `status` 不被删除阶段覆盖：复制成功的对象 `status` 保持 `'success'`，删除结果通过 `sourceDeleteStatus` 表达。最终移动结果由两者共同决定（见 3.5 summary 计算）。

### 3.4 执行流程

```ts
// server/utils/executors/move.ts
import { copyObjectsPhase } from './copy'
import { deleteObjects } from '#server/utils/minio'
import type { TaskExecutor, TaskEvent, Task } from '#server/utils/task-manager'

export function createMoveExecutor(params: MoveParams): TaskExecutor {
  return {
    async execute(task: Task, emit: (e: TaskEvent) => void, isCancelled: () => boolean) {
      const { sourceInstance, sourceBucket, targetInstance, targetBucket } = params

      // —— 阶段 1：复制 ——
      task.currentPhase = 'copying'
      emit({ event: 'phase', data: { taskId: task.taskId, phase: 'copying' } })

      const copiedKeys = await copyObjectsPhase(task, emit, isCancelled, params)
      // copyObjectsPhase 内部：
      //   - collectObjectsByPrefixes 收集全部 key
      //   - 逐个 copyObjectStream，更新 task.fileProgress.results[key].status
      //   - 每个 key 发 progress 事件（running -> success/failed）
      //   - 返回复制成功的 key 列表

      if (isCancelled()) return  // 复制阶段取消，不进入删除

      // —— 阶段 2：删除源对象 ——
      if (copiedKeys.length > 0) {
        task.currentPhase = 'deleting'
        emit({ event: 'phase', data: { taskId: task.taskId, phase: 'deleting' } })

        // deleteObjects 一次性批量删除（内部自动分批每 1000 个），
        // 返回 { deleted: string[], errors: { key, error }[] }
        const result = await deleteObjects(sourceInstance, sourceBucket, copiedKeys)

        // 逐个更新 fileProgress 并发 progress 事件
        for (const key of result.deleted) {
          task.fileProgress.results[key].sourceDeleteStatus = 'deleted'
          emit({
            event: 'progress',
            data: { taskId: task.taskId, objectKey: key,
                    result: { ...task.fileProgress.results[key] } },
          })
        }
        for (const err of result.errors) {
          task.fileProgress.results[err.key].sourceDeleteStatus = 'delete-failed'
          task.fileProgress.results[err.key].sourceDeleteError = err.error
          emit({
            event: 'progress',
            data: { taskId: task.taskId, objectKey: err.key,
                    result: { ...task.fileProgress.results[err.key] } },
          })
        }
      }

      // —— 汇总 ——
      task.summary = computeMoveSummary(task.fileProgress.results)
    },
  }
}
```

**删除阶段进度特点**：`deleteObjects` 是 S3 DeleteMultipleObjects 批量调用，一次性返回全部结果（内部自动分批），不像复制阶段逐文件流式推进。因此删除阶段无"逐个删除"的实时进度，而是 `deleteObjects` 返回后一次性更新所有删源状态。前端在 `deleting` 阶段显示 spinner，结果返回后一次性刷新删源图标。

### 3.5 summary 计算

```ts
function computeMoveSummary(results: Record<string, FileResult>): TaskSummary {
  let success = 0, failed = 0, skipped = 0
  for (const r of Object.values(results)) {
    if (r.status === 'skipped') { skipped++; continue }
    if (r.status === 'failed') { failed++; continue }            // 复制失败
    // status === 'success'（复制成功），看删除结果
    if (r.sourceDeleteStatus === 'deleted') success++
    else if (r.sourceDeleteStatus === 'delete-failed') failed++  // 删除失败
    // sourceDeleteStatus === undefined：复制成功但未及删除（取消），计入 failed
    else failed++
  }
  return { total: Object.keys(results).length, success, failed, skipped }
}
```

- `success` = 复制成功且删除成功
- `failed` = 复制失败 + 删除失败 + 复制成功但未删除（取消中断）
- `skipped` = 取消时未开始的对象

### 3.6 取消行为

取消通过 `isCancelled()` 检查点实现，行为因阶段而异：

| 取消时机 | 目标侧 | 源侧 | 等效状态 | 用户后续动作 |
|----------|--------|------|----------|-------------|
| 复制阶段 | 已复制的对象保留 | 未删除 | 等同部分复制 | 目标侧有部分副本，源完整；可重新移动或手动清理目标 |
| 删除阶段 | 已复制的对象保留 | 部分源已删 | 源和目标都有副本 | **需手动检查**：确认哪些源已删，清理重复副本 |

复制阶段的检查点在每个文件复制前（`copyObjectsPhase` 内部循环开头）；删除阶段的检查点在进入删除阶段前（`if (isCancelled()) return`，不发起删除）。由于 `deleteObjects` 是一次性批量调用，删除阶段中途无法逐文件中断——一旦发起删除即等待该批完成。

> 取消后未开始复制的对象标记 `status: 'skipped'`，复制中断的对象保持上一个状态。

## 4. API 改造

### POST /api/browse/objects/move

改为返回 `{ taskId }`，不再返回 SSE 流。SSE 订阅走通用端点 `GET /api/tasks/:taskId/events`。

```ts
// server/api/browse/objects/move.post.ts
import { getGroups } from '#server/utils/store'
import { collectObjectsByPrefixes } from '#server/utils/minio'
import { createTask } from '#server/utils/task-manager'
import { createMoveExecutor } from '#server/utils/executors/move'
import type { MinioInstance } from '#shared/schemas/groups'

export default defineEventHandler(async (event) => {
  const body = await readBody<CopyMoveRequest>(event)

  // 1. 参数校验（同当前实现）
  if (!body?.sourceInstanceId || !body?.targetInstanceId) {
    throw createError({ statusCode: 400, message: '缺少源/目标实例 ID' })
  }
  if (!body?.sourceBucket || !body?.targetBucket) {
    throw createError({ statusCode: 400, message: '缺少源/目标 bucket' })
  }

  // 2. 查找源/目标实例（同当前实现）
  const allGroups = await getGroups()
  const findInstance = (id: string): MinioInstance | undefined => { /* ... */ }
  const sourceInstance = findInstance(body.sourceInstanceId)
  const targetInstance = findInstance(body.targetInstanceId)
  if (!sourceInstance) throw createError({ statusCode: 404, message: '未找到源实例' })
  if (!targetInstance) throw createError({ statusCode: 404, message: '未找到目标实例' })

  // 3. 构造 TaskDescription
  const objectCount = body.keys.length + body.prefixes.length  // 选中项数（未展开）
  const description: TaskDescription = {
    type: 'move',
    label: `移动 ${objectCount} 个对象`,
    detail: `${sourceInstance.name}/${body.sourceBucket} -> ${targetInstance.name}/${body.targetBucket}`,
  }

  // 4. 创建任务（executor 闭包捕获参数），返回 taskId
  const executor = createMoveExecutor({
    sourceInstance, sourceBucket: body.sourceBucket, sourcePrefix: body.sourcePrefix,
    keys: body.keys, prefixes: body.prefixes,
    targetInstance, targetBucket: body.targetBucket, targetPrefix: body.targetPrefix,
  })
  const taskId = createTask(description, executor)

  return { taskId }
})
```

- 请求体 `CopyMoveRequest` 与 copy 完全相同（`sourceInstanceId` / `sourceBucket` / `sourcePrefix` / `keys` / `prefixes` / `targetInstanceId` / `targetBucket` / `targetPrefix`）
- `createTask` 内部决定立即执行或入队，前端凭 `taskId` 订阅进度
- 同源同路径校验（`isSamePath`）在前端提交前拦截，后端不再重复校验

## 5. 前端改造

### 5.1 browse-copy-move-modal.vue（move 部分）

与 copy 共用组件，改造一并进行。move 专属的差异点：

**提交方式**：

```ts
async function startTransfer() {
  // 构造请求体（同当前）
  const body = { /* sourceInstanceId, ..., targetPrefix */ }

  // POST 提交，拿 taskId
  const { taskId } = await $fetch<{ taskId: string }>(
    `/api/browse/objects/move`, { method: 'POST', body }
  )

  // 通过 useTaskManager 订阅进度（EventSource GET）
  const { subscribeTask } = useTaskManager()
  await subscribeTask(taskId, handleTaskEvent)
}
```

**事件处理**：用通用 `TaskEvent` 替代当前自定义 SSE 事件，映射关系：

| 当前事件 | 通用事件 | 处理 |
|----------|----------|------|
| `total` | （copyObjectsPhase 内部已知总数，前端从 state 快照获取 `fileProgress` 长度） | 初始化文件列表 |
| `start` | `progress`（`status: 'running'`） | 文件置 pending/running |
| `progress`（success/failed） | `progress`（`status: 'success'/'failed'`） | 更新复制状态 |
| `deleting` | `phase`（`phase: 'deleting'`） | 切换阶段标签 |
| `source-deleted` | `progress`（`sourceDeleteStatus: 'deleted'/'delete-failed'`） | 更新删源状态 |
| `done` | `complete`（`summary`） | 进入完成态 |
| `error` | `error` | toast 提示 |

**阶段标签**：根据 `currentPhase` 展示当前阶段：

| `currentPhase` | 标签 | 说明 |
|----------------|------|------|
| `'copying'` | `复制中` | 复制阶段，文件项显示复制状态 |
| `'deleting'` | `删除源` | 删除阶段，文件项显示删源状态 + spinner |

进度条按阶段分别计算：
- `copying` 阶段：进度 = 复制成功数 / 总数
- `deleting` 阶段：进度 = 删源成功数 / 待删除数（即复制成功数）

**后台继续**：执行阶段弹窗可关闭（与当前 `:dismissible=false` 不同），任务在后端继续，通过导航栏任务查看器查看进度。重连恢复由 `useTaskManager.subscribeTask` 从 `GET /api/tasks/:taskId/state` 拉取快照重建视图。

**完成后**：
- 全部成功：toast 提示 + 刷新对象列表（源对象已删，需刷新）
- 有失败：弹窗内显示失败项 + 错误信息；若存在"复制成功但删除失败"的项，错误信息提示"源和目标可能都有副本，请手动检查"

### 5.2 与 copy 共用的改造点

以下改造 copy/move 共用，详见复制技术方案：

- 提交方式从 `fetch + reader`（POST SSE）改为 `$fetch` 拿 `taskId` + `useTaskManager.subscribeTask`（GET EventSource）
- 弹窗 `:dismissible` 执行阶段改为可关闭（后台继续）
- 进度数据源从组件内 `targetProgress` 改为 `useTaskManager` 的 `activeTask`（`fileProgress` + `currentPhase`）

## 8. 风险：非原子性

移动 = 复制 + 删除两阶段，**非原子操作**。中途取消或失败可能出现"源和目标都有副本"的中间状态：

| 场景 | 中间状态 | 处理建议 |
|------|----------|----------|
| 复制阶段取消 | 目标有部分副本，源完整 | 目标副本可手动删除或重新移动覆盖 |
| 复制阶段失败（部分文件复制失败） | 复制成功的文件在目标有副本，源完整 | 删除阶段仍会删除已成功复制的源对象；复制失败的对象源保留 |
| 删除阶段失败（部分源删除失败） | 目标全量副本，源部分残留 | 复制成功的对象已在目标，残留源对象需手动删除 |
| 删除阶段取消 | 目标全量副本，源部分已删 | **源和目标都有副本**，需手动核对去重 |
| 进程重启 | 任务丢失，两阶段中断处状态不明 | 内存态任务丢失，需手动核对源与目标 |

**错误信息提示**：当移动任务存在失败项（含删除失败）或被取消时，完成态的错误/提示信息中明确提示用户："移动非原子操作，可能出现源和目标都存在副本的情况，请手动检查并清理重复对象。"

**不自动回滚**：参照通用框架"失败透明、不自动重试"的设计哲学，移动失败不自动回滚已复制的对象或已删除的源，由用户决定后续动作。

**与同 bucket 移动的注意**：同实例同 bucket 不同前缀的移动，复制阶段会先在目标前缀生成副本，删除阶段再删源前缀对象。若目标前缀是源前缀的子路径（如源 `a/` -> 目标 `a/b/`），`collectObjectsByPrefixes` 在复制前已收集完 key 快照，不会因复制产生的新对象而误删——但仍建议用户避免这种嵌套移动以免混淆。
